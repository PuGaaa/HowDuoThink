# 篇-章-关三级内容架构 + 100 关扩展路线

## 一、组织方式定稿（已确认）

```
篇 Part（按难度三篇：侦探学徒 → 一线工兵 → 资深值班）
 └ 章 Chapter（= 层的契约，每章 6~12 关封顶）
    └ 关 Level（= 故障案例：layer + typeTags + difficulty + source）
```

- **章 = 层契约**（灵魂不变），篇解决导航规模，类型标签解决“想练什么”
- **关带元数据、章动态聚合**（取代硬编码 cases 清单）：加第 101 关只需打 `layer + typeTags`，自动归位；社区精选关可晋升进官方路径
- 官方/社区并存：社区关默认在“社区关卡”区，管理端深度加工后可标“精选”晋升进对应章

## 二、数据结构改造

**case 元数据（types/case.ts 扩展）**：
```ts
interface DiagnosisCase {
  ...现有字段
  part: 'apprentice' | 'engineer' | 'master'   // 篇
  typeTags: string[]                            // 故障机理标签：config/dependency/race/resource/capacity/cert/timing/security
}
```

**chapters.ts 重构**（从“章含关清单”改为“章定义 + 动态聚合”）：
```ts
interface PartDef { id, name, desc }                    // 三篇
interface ChapterDef { id, part, no, name, pact }       // 章定义（不再列 cases）
// 章内容 = ALL_CASES.filter(layer 归属) 动态聚合，顺序按 case.order 字段
```
Case 增加 `layer` 结构化字段 + `order`（章内排序）。`getCaseById` 兼容：本地 ALL_CASES + casepack 远端 case 合并查找（为 P4 铺路）。

**篇定义（难度三篇）**：
- 侦探学徒篇 apprentice：各层入门 1~2 关（教学关 L1 集中地）
- 一线工兵篇 engineer：标准难度主力（L2）
- 资深值班篇 master：L3 地狱关 + 双因叠加

## 三、100 关内容路线图（篇 × 章 × 类型标签矩阵）

现有 4 章扩展为 8 章（每章 6~12 关封顶）：

| 篇 | 章（层） | 目标关数 |
|---|---|---|
| 学徒 | 接入层之夜（TLS/DNS/CORS/Nginx）、构建与依赖（白屏/依赖） | 各 4~6 |
| 工兵 | 数据的脾气（连接池/缓存/主从/慢查询）、运行时暗面（OOM/文件句柄/线程）、并发迷宫（锁/竞态/幂等） | 各 8~10 |
| 值班 | 可观测性迷雾（日志丢失/指标误导/告警风暴）、安全与配置（权限/密钥/环境差异）、容量与降级（限流击穿/扩容/降级） | 各 8~12 |

100 关 = 8 章 × 12 关左右。**typeTags 词表**（初版 8 个）：config（配置错误）、dependency（依赖故障）、race（竞态）、resource（资源泄漏）、capacity（容量）、cert（证书与信任）、timing（时间与顺序）、data（数据一致）。新类型按需扩词表。

## 四、实施批次

**P1 数据结构改造（App 端）**
1. types/case.ts 加 part/typeTags/order/layer 结构化字段
2. chapters.ts 重构（PartDef/ChapterDef + 动态聚合），index.uvue 首页改篇-章两级导航（篇折叠 + 章卡）

4. 存量 ssl-chain 打标（part: engineer 或 apprentice 视难度——当前 L2 标 engineer）

**P5 出题批次二**（工兵篇主力 6 关 + 值班篇开张）+ 部署

## 五、验证方式

App：篇折叠导航（三篇展开/收起）、章内关卡聚合正确、新关加入不动配置数组即可归位；Web：解决逻辑列表带篇/章/类型标签筛选。
