# 独立管理端 + 监控机制 实施计划

## 决策记录（将写入 docs/decisions/006-独立管理端与监控.md）

- **推翻 003 的形态决策**：管理端从 web /admin 迁出为独立工程（理由：管理能力膨胀到用户/成本/运营/健康四域，与社区站分离鉴权与部署）；003 的内容飞轮流程决策继续有效。
- **监控走混合路线**：可用性/错误告警用免费 SaaS（UptimeRobot 拨测 + Sentry 错误追踪）；AI 用量、业务指标、资源水位自建落库进管理端看板；本机不跑 Prometheus/Grafana（2G 内存约束），将来需要时用 remote_write 接 Grafana Cloud。

## 一、独立管理端工程 `admin/`（仓库顶层，与 web/server/app 平级）

- **技术栈**：Vite + Vue 3 + TypeScript SPA（后台无 SSR 需求，比 Nuxt 轻；与项目 Vue 习惯一致）+ Naive UI（表格/表单密集型管理页提效）+ vue-router。状态用 composables，不引 Pinia。
- **目录**（按 features 垂直切片）：
  ```
  admin/src/features/
    auth/      登录页 + api
    content/   投稿审核页、Case 列表页、Case 编辑页（自 web /admin 迁移）
    users/     用户管理页
    ai-usage/  AI 用量与成本页
    stats/     运营数据看板页
    ops/       服务健康页
  admin/src/{components,utils,styles,router,api}
  ```
- **鉴权**：复用现有 `/api/auth/login` 的 JWT，走 `Authorization: Bearer`（deps.py 已支持，不动 cookie 域）；全局路由守卫，未登录跳登录页。server `core/config.py` 加 `ADMIN_WEB_ORIGIN` 并入 CORS 白名单。dev 环境继续可用 `/api/dev/login`。
- **托管**：Dockerfile 多阶段构建（node 层 build admin → 产物进 api 镜像），FastAPI StaticFiles 挂 `/admin/`（SPA fallback）。不加新容器、不加内存占用，一条 `docker compose up -d --build` 拉起整套。本地开发用 vite dev server proxy 到 :8000。

## 二、server 端新增（全部按 feature 架构落位）

1. **用户管理**（新域 `features/users/`，router/service/models）：
   - `users` 表加 `status` 列（active/banned），按 db.py 现有模式做 SQLite/MySQL 双份内联轻迁移。
   - 接口：`GET /api/admin/users`（分页搜索，限最大页容量）、`PATCH /api/admin/users/{id}/role`（禁自降级、禁降最后一个 admin）、`PATCH /api/admin/users/{id}/status`（封禁/解封），Pydantic 出入参。
   - 封禁生效：`current_user` 验 token 后查库校验 status；三种登录入口（账密/OAuth/短信）拒绝 banned 用户。
2. **AI 用量审计**（features/ai 内）：
   - 新表 `ai_usage(id, uid, kind[chat|draft|embed], prompt_tokens, completion_tokens, duration_ms, ok, created_at)`。
   - 埋点：`node_answer`/`node_draft` 从 LangChain 响应取 `response_metadata.token_usage`；embed 记耗时/条数；审计写入失败只 warning 不影响主流程；无 key 降级路径写 `ok=0` 供排障。
   - 查询：按日汇总 + 按用户 TOP 两个 admin 端点；成本单价走 env（`DEEPSEEK_PRICE_IN/OUT`，元/百万 tokens）。这同时是 005 P2 配额产品化的数据地基。
3. **运营统计**（新域 `features/stats/`）：
   - 活跃底座表 `user_activity(user_id, day, PK(user_id,day))`，在登录成功、casepack 同步、progress 保存三入口幂等 upsert。
   - `GET /api/admin/stats/overview?days=30`：DAU、新增用户、投稿量/采纳率、案例发布数、活跃趋势。完关率依赖 App 端 progress payload 结构，实施时先尝试解析；不可解析则第一版以"活跃用户"口径上并注明待对齐。
4. **服务健康（自建半边）**：
   - main.py 现有 rid 中间件顺带进程内计数（请求数/错误数/耗时）。
   - 快照表 `ops_snapshots`：后台线程每 5 分钟写 RSS/磁盘水位/请求错误计数，保留 30 天。
   - `GET /api/admin/ops/health`：实时水位 + mysql 连通 + casepackVersion。
   - compose 给 api 容器补 healthcheck（现仅 mysql 有）。
5. **Sentry**：server 接 `sentry-sdk[fastapi]`，`SENTRY_DSN` 空=关闭（运行时降级，环境仍同构）；admin 前端接 @sentry/vue。

## 三、web 侧清理

admin 工程验收后：删除 `web/pages/admin/` 两页、`web/app.vue` 中管理端菜单入口。**迁移顺带修复已确认的 bug**：`admin/index.vue` 中 `makeAiDraft`/`reindex`/`reindexing`/`aiBusyId`/`reindexMsg`/`aiWarning` 未定义（按钮点击即报错，B19 误记为已落地）。

## 四、实施顺序（5 个阶段，每阶段可独立验收）

1. **骨架 + 内容管理迁移**：admin 工程骨架 → CORS → 迁移审核/Case 编辑/发布/重建索引（修 bug）→ 静态托管 → web 下线旧管理页。验收：登录→审核→AI 预填→编辑→发布全链路通。
2. **用户管理**：status 迁移 → 封禁链路 → users 接口 + 管理页。验收：封禁立即 401、角色变更即时生效、防自降级。
3. **AI 用量与成本**：ai_usage 表 + 埋点 + 用量页。验收：一次对话/起草在看板产生 token 与成本记录。
4. **运营看板**：user_activity + 三入口 upsert → stats 接口 + 概览页。验收：造数后指标正确。
5. **健康与告警 + 文档**：ops 快照/健康页 → compose healthcheck → Sentry/UptimeRobot 接入文档 → 006 决策文档 → 部署文档更新 → B19 勘误记录。

## 五、测试与风险

- server 端核心逻辑补 pytest（users 接口/封禁链路/ai_usage 埋点/stats 聚合），外部依赖 mock；admin 以页面 E2E 验收（浏览器工具走真实链路）。
- 风险控制：轻迁移双 SCHEMA 同步；current_user 查库在当前用户量级无压力；聚合 SQL 只走 day/uid 索引列，不扫 payload TEXT；镜像构建新增 node 层会拉长 build 时间（可接受）。
