> 版本：v1.1 ｜ 状态：持续迭代中（实现状态见 ROADMAP 与改造计划执行记录）｜ 更新日期：2026-11-04

## 一、产品概述

### 1.1 产品名称

**好多星** — 诊断思维训练场

### 1.2 一句话定位

好多星 是一座住满"思维兽"的训练场——用真实故障当教材，训练工程师的思考方式。**解决问题只是过程，思维晋升才是结果。**

### 1.3 解决什么问题

agent 时代的程序员面临三个核心痛点：

| 痛点 | 表现 | 好多星 的解法 |
|---|---|---|
| 会写代码但不会排查 | 能 CRUD 但面对故障时不知道从哪下手 | 131 个正式案例，训练"看症状→建假设→算成本→定根因"的核心习惯 |
| 知识碎片化没有体系 | 会修单个 bug 但没有全栈视野 | 16 章组成学徒/工兵/大师三篇学习路径 |
| 经验无法沉淀 | 修过的 bug 下次还会踩 | 每关带走检查单，积累为个人诊断手册 |

### 1.4 核心理念

**解决问题是过程，思维晋升才是结果。**

训练的不是知识点，而是高手的核心习惯——看症状、建假设、算成本、定根因。每个案例都来自真实世界；脱离真实场景的刷题不产生思维。

### 1.5 目标用户

| 用户画像 | 年限 | 核心诉求 | 使用方式 |
|---|---|---|---|
| **P1 初级工程师** | 0~2 年 | 会 CRUD 但不会排查——需要方法论 | 闯关 L1~L2，收集检查单 |
| **P2 中级工程师** | 2~5 年 | 能修但没体系——需要思维框架 | 闯关 L2~L3，对照专家链查盲区 |
| **P3 高级/负责人** | 5 年+ | 想验证团队思维盲区 | 评审/决策模式，模拟团队场景 |
| **P4 团队负责人** | 管理 | 新人培训工具——需要章节数据追踪成长 | 分配章节 + 查看进度 |

## 二、思维体系（产品内核）

四层十一思——产品的思维训练目标体系，每一关都标注主训/次训思维。

### 视野层 —— 看得全

| 思维 | 训练什么 |
|---|---|
| 全栈视野 | 接入/构建/数据/运行时/并发/可观测六大层——先画圈再下钻 |
| 产品思维 | 影响面的本质是用户体验：故障对业务/用户意味着什么 |
| 安全思维 | 证书链/鉴权/注入——每个故障都可能是安全问题的冰山一角 |

### 推理层 —— 想得深

| 思维 | 训练什么 |
|---|---|
| 假设思维 | 候选假设集，而非瞎猜 |
| 成本思维 | 按验证成本排序，最小代价定位 |
| 验证思维 | 证据说话，实锤再指认 |

### 设计层 —— 追得远

| 思维 | 训练什么 |
|---|---|
| 架构设计思维 | 故障的种子是设计取舍：缓存窗口、重试风暴、超时级联、幂等缺失 |
| 程序设计思维 | 代码边界/状态管理/防御式编程 |

### 沉淀层 —— 留得下

| 思维/知识 | 训练什么 |
|---|---|
| 复盘思维 | 检查单 = 把经验变成防御 |
| 拓展知识 | 层契约知识（TLS 握手/索引原理/协议行为） |

## 三、皮肤体系（关卡表现形式）

诊断/侦探/值班/评审 = 皮肤（关卡的表现形式，会演进）；思维训练 = 内核（不变）。

| 皮肤 | 玩法 | 训练侧重 | 占比 |
|---|---|---|---|
| **排查现场** | 事后故障排查：看症状→建假设→验证→指认根因 | 推理层三思 + 全栈视野 | ~70% |
| **评审现场** | 事前设计评审：审方案→找缺陷→出修正清单 | 架构设计 + 程序设计 | ~20% |
| **决策现场** | 实时权衡决策：信息不完整→评估→做决定 | 产品思维 + 安全思维 | ~10% |

## 四、功能需求

### F1 闯关系统（核心功能）

**描述**：131 个正式案例，16 章 × 3 篇（学徒/工兵/大师），序贯解锁 + 跳级挑战；游客固定体验三关，登录用于保存进度并继续学习。

**用户故事**：
- 作为 P1 用户，我想选择一个章节开始闯关，以便系统学习某一层的排错思维。
- 作为 P2 用户，我想查看每关的专家推理链，以便对照自己的思路找到盲区。
- 作为用户，我想在假设板上自由勾选怀疑对象，以便按我的直觉探索（验证错了可以返回重新假设）。

**验收标准**：
- Given 用户已注册，When 用户进入章节详情页，Then 显示该章所有关卡及解锁状态
- Given 用户未解锁第 N+1 章，When 用户尝试直接访问，Then 提示需要完成前置章节
- Given 用户选择了假设并点击"开查"，Then 系统按假设过滤可用的验证动作
- Given 用户指认根因正确，Then 显示 S/A/B 评级 + 专家推理链 + 检查单带走
- Given 用户未执行任何验证动作，When 尝试指认根因，Then 被引导先做验证（不消耗机会）
- Given 用户指认根因错误，Then 扣除一次错误指认机会（2 次后出局）
- Given 用户本局失败，Then 章节地图该关标"未破"并引导重练；当日连续天数不因失败续期

**关键机制**：
| 机制 | 说明 |
|---|---|
| ⚡ 预算 | 每个验证动作消耗 ⚡，专家链有基准成本——消耗越少评级越高 |
| 假设板 | 全程可编辑，假设驱动验证动作的可见性 |
| 错误指认 | 证据门：未做任何验证不许指认（不扣机会）；2 次机会，第 2 次错误 → 出局 |
| 失败留痕 | 失败计入关卡 fails；章节地图标"未破"引导错案重练；连续天数仅破案累计 |
| 评级 | S（根因对 + 预算 ≤1.2x + 零错误）/ A / B / F |
| 序贯解锁 | 前章破 ≥1 关解锁本章 |
| 跳级挑战 | 锁定章首关恒可玩，通关即解锁整章 |

**章节结构**：

| 章 | 名称 | 主训 | 关数 |
|---|---|---|---|
| 1 接入层之夜 | DNS/TLS/CORS/网关 | 全栈视野 | 5 |
| 2 构建与依赖 | 白屏/依赖冲突/CI | 验证思维 | 5 |
| 3 数据的脾气 | 连接池/缓存/慢查询/评审 | 架构设计 | 6 |
| 4 运行时暗面 | OOM/事件循环/TIME_WAIT/闭包/泄漏续集 | 程序设计 | 5 |
| 5 并发迷宫 | 超卖/幂等/消息乱序/假线索 | 假设思维 | 4 |
| 6 可观测性迷雾 | 日志采样/平均指标/告警风暴/直方图 | 验证思维+产品思维 | 5 |
| 7 安全攻防 | 密钥/IDOR/日志PII/SSRF/竞态/供应链 | 安全思维 | 6 |
| 8 架构演进 | 限流/降级/重试/HPA | 架构设计+产品思维 | 4 |

### F2 假设板（核心机制）

**描述**：每关开局提供 3~8 个候选假设（含干扰项），用户勾选怀疑对象后，系统按假设过滤可用的验证动作。假设板全程可编辑——验证错了随时"返回重新假设"。

**用户故事**：
- 作为用户，我想在假设板上勾选我的怀疑，以便系统只展示我关心的验证手段。
- 作为用户，我想在验证过程中修改假设（返回重新假设），以便根据新证据调整方向。

**验收标准**：
- Given 假设板展示 3~8 个假设，When 用户勾选 ≥1 个假设并点击"开查"，Then 验证动作列表按勾选假设过滤
- Given 用户在验证过程中返回假设板修改勾选，When 用户确认后，Then 验证动作列表实时更新
- Given 用户未勾选任何假设直接点"开查"，Then 提示"至少先立一个假设"

### F3 情绪兽系统（差异化功能）

**描述**：五只思维兽外化排错时的五种情绪——恐慌蛙（慌张）、不行蜗（迟疑）、惊讶獭（意外）、垂耳兔（沮丧）、三角龙（坚定）。在关键节点出场，让用户看见并驯服自己的情绪。

**用户故事**：
- 作为用户，我想在排错卡壳时看到"不行蜗"告诉我"迟疑是正常的"，以便接受情绪继续推进。

**出场节点**：
| 情绪兽 | 触发时机 | 台词方向 |
|---|---|---|
| 恐怖蛙 | 看到大量报错时 | "好多红色！恐慌不产生信息。" |
| 惊讶獭 | 读到关键证据时 | "这条线索值回票价！" |
| 不行蜗 | 排查迟疑/卡壳时 | "迟疑是正常的。" |
| 垂耳兔 | 错误指认后 | "证据链指向了别处。" |
| 三角龙 | 根因锁定时 | "稳了。" |

---

### F4 检查单系统（沉淀功能）

**描述**：每关通关后带走 3~4 条"诊断检查单"（思维型 ≥3 + 知识型 ≤1），积累为个人"诊断手册"。

**用户故事**：
- 作为用户，我想在指认根因前核对我的检查单，以便用历史经验辅助当前决策。
- 作为用户，我想在手册页看到所有已收集的检查单，以便回顾我的思维成长。

**验收标准**：
- Given 用户通关一关，Then 手册新增该关的检查单（3~4 条）
- Given 用户进入指认根因 tab，Then 显示"指认前核对：我的检查单（N）"可展开
- Given 检查单为空，Then 显示"还没有检查单——破案后会在这里积累"

---

### F5 复盘系统（学习闭环）

**描述**：通关后进入复盘室，包含：S/A/B/F 评级 + 五兽庆祝 + 专家推理链（逐步展开）+ 心理回放（情绪兽出场回顾）+ 假设板终局对照 + 检查单带走。

**用户故事**：
- 作为用户，我想逐步展开专家推理链，以便对照自己的每一步和专家的每一步。
- 作为用户，我想看到心理回放（情绪兽在关键节点的出场），以便意识到自己的情绪变化。

**验收标准**：
- Given 用户通关，Then 显示评级（S/A/B/F）+ 成本对比（你 vs 专家）+ 五兽庆祝
- Given 用户展开推理链，Then 每步显示：观察→判断→动作→为什么→结论
- Given 用户有错误指认，Then 心理回放显示垂耳兔的引导

### F6 任务系统（留存功能）

**描述**：每日 ×4 + 每周 ×2 + 成长 ×2 的任务体系，进度环可视化。

**任务清单**：
| 类型 | 任务 | 条件 |
|---|---|---|
| 每日 | 今日首胜：破案 1 关 | win ≥ 1 |
| 每日 | 复习检查单 1 次 | checkuse ≥ 1 |
| 每日 | 立假设 ≥2 个 | hypo ≥ 2 |
| 每日 | 完成今日一题 | dailycase ≥ 1 |
| 每周 | 本周破案 3 关 | casewin7 ≥ 3 |
| 每周 | 集齐 2 个不同层的检查单 | layers2 ≥ 2 |
| 成长 | 晋升「主治工程师」 | solved ≥ 3 |
| 成长 | 全部章节通关 | solved = ALL |

### F7 登录与账号

**描述**：双通道登录（手机验证码 + 密码），Bearer token 认证，多身份绑定。

**用户故事**：
- 作为用户，我想用手机验证码登录，以便快速上手（不需要记密码）。
- 作为用户，我想在 Web 端用 GitHub 登录后在 App 端用验证码登录同一账号，以便多端互通。

**登录方式**：
| 方式 | 通道 | 互通 |
|---|---|---|
| 手机验证码 | Bearer token | 新号自动建（可爱代号昵称），绑定后与 Web 互通 |
| 账号密码 | Bearer token | Web 端注册的账号直接登录 |
| GitHub OAuth | Web 端专属 | Web 端 GitHub 注册的账号 App 端用验证码登录 |

**验收标准**：
- Given 用户输入正确手机号 + 验证码，When 提交登录，Then 返回 token + 用户信息 + 可爱代号昵称
- Given 用户已通过 GitHub 注册并绑定手机号，When 用手机验证码登录，Then 返回同一账号
- Given 用户用密码登录（Web 注册的），When 用手机验证码登录，Then 返回同一账号（已绑定）

---

### F8 检查单云同步（多端互通）

**描述**：登录态下拉取合并服务器进度（服务器有本地无 → 补入；冲突 solved 并集）+ 破案后 2s 防抖全量上传。

**用户故事**：
- 作为用户，我想在换设备后自动恢复我的进度，以便无缝继续学习。

**同步策略**：
| 场景 | 行为 |
|---|---|
| 登录后首次打开 | 拉取服务器进度，本地没有的补入，冲突取 solved=true 并集 |
| 通关一关 | 2s 防抖全量上传（仅登录态） |
| 退出登录 | 清除同步标记（不清本地数据） |

## 六、用户流程

### 新用户首次打开

```
首页（章节地图 + 今日一题横幅）
  → 选章（第 1 章 接入层之夜）
  → 闯关（假设板 → 验证 → 指认根因）
  → 复盘（S 评级 + 专家推理链 + 检查单 ×4）
  → 解锁下一章
  → 收集检查单 → 手册越来越厚
  → 分享海报
```

### 回流用户

```
登录（验证码/密码）
  → 云同步自动拉取（进度合并）
  → 继续闯关（上次进度）
  → 破案 → 自动上传
  → 分享海报
```

### 内容生产者（Web 端）

```
投稿（真实故障：症状+现象+解决过程）
  → 管理端审核（接受/拒绝）
  → AI 辅助转稿（投稿 → 关卡草稿）
  → 编辑润色 → 发布
  → App + Web 同步展示
```
