# 007 · 工程规范与质量门禁

日期：2026-11-03 · 状态：已定（护栏批次实施中）

## 决策

| 议题 | 决策 | 理由 |
|---|---|---|
| 目标形态 | 单人打底 + 演进位 | 现状单人 + AI 协作；自动化门禁为纲，每个制度标注多人时的升级路径（见研发流程.md ③④） |
| 合并门禁 | CI 四 job（server / security / admin / web）全仓必过 | 质量由机器强制；admin/web 含类型检查，server 含 lint+测试+密钥扫描+依赖漏洞扫描 |
| 依赖管理 | pip-tools 双 lock（runtime/dev），dev/CI/镜像统一 Python 3.12 | 构建可复现是"环境只允许配置不同"红线的前提 |
| 数据库迁移 | Alembic（梯队二） | 行业标准；与方言翻译体系的张力用"单 revision 双引擎分支"化解（规格 §5.1） |
| 门禁哲学 | 验收标准是"验证过拦截"，不是"配置了" | 用真实坏提交验证门禁真的拦得住；假完成比没有门禁更危险 |
| 评审形态 | 独立评审子代理 + 自审底线（测试证据） | 单人阶段用 AI 评审买"第二双眼睛"；多人时升级人工 reviewer |

## 明确不做（当前阶段）

- 不引入 Prometheus/Grafana、monorepo 工具链等重基础设施
- 不启用 CODEOWNERS / 多环境审批流（只登记在演进位）
- 不做前端 eslint（类型检查先行，YAGNI）
