# 研发流程

> 本文档是工程规范化的日常执行面（规格见
> `docs/superpowers/specs/2026-10-30-engineering-standardization-design.md`，
> 决策依据见 `docs/decisions/007-工程规范与质量门禁.md`）。
> 原则：质量由门禁强制，不依赖人的自觉；门禁的验收标准是"验证过拦截"，不是"配置了"。

## ① 分支与提交规范

- **分支命名**：`feat/<主题>` / `fix/<主题>` / `docs/<主题>` / `build|ci|style|refactor/<主题>`。
- **提交信息**：conventional commits（`feat: / fix: / docs: / style: / refactor: / build: / ci:`），
  正文写清动机与验证方式；一次提交一个意图。
- **main 保护**：禁直推，四个 CI job（`server` / `security` / `admin` / `web`）全绿才可合并。
  单人开发也走 PR——门禁防的是手滑，不是他人。
- **依赖升级**：改 `server/requirements*.in` → `pip-compile` 生成 lock → lock 进 PR 评审。
  禁止手改 lock 文件。

## ② 完成定义（DoD）

一个功能算完成，必须五项俱全：

1. **代码**——分层与约束符合 AGENTS.md（feature 架构、方言翻译、环境同构红线）
2. **测试**——新增行为有测试且看过它失败；全套件绿
3. **文档**——README / 流程文档 / ADR 涉及时更新
4. **配置项**——新增配置已注册（`core/settings` 或 `.env.example`）并写默认值
5. **审计点**——涉及权限 / 资金 / 内容变更的操作记录操作者

## ③ 评审流程

- **当前（单人 + AI）**：每个批次完成后，由**独立评审子代理**（全新上下文）对整支分支评审，
  Critical/Important 修复后重验，Minor 记录延后；评审聚焦点取自计划文档的"评审聚焦点"一节。
- **自审底线**：每条"完成"断言必须附刚跑过的命令与输出（测试证据进 PR 描述）。
- **演进位（多人时）**：升级为人工 reviewer + CODEOWNERS，评审记录留档。

## ④ 发布与回滚

- **发布**：镜像 tag = git tag；`server/Dockerfile` 与 `docker-compose.yml` 为唯一部署真相，
  变更走 PR。
- **变更记录**：对外可见的行为变更在 PR 描述列出；破坏性变更（schema、配置键删除）单独标注。
- **回滚**：镜像回退上一个 tag；数据库回滚依赖迁移的 `downgrade()`（梯队二落地后）。
- **红线**：任何部署变更必须能回答"dev 和 prod 是不是同一种东西"（AGENTS.md 环境一致性）。

## ⑤ 附录

### 分支保护手动配置步骤

GitHub → `PuGaaa/HowDuoThink` → Settings → Branches → Add branch protection rule：

1. Branch name pattern：`main`
2. ✅ Require a pull request before merging（单人开发不勾 Require approvals）
3. ✅ Require status checks to pass before merging → 搜索并勾选四个 check：
   `server`、`security`、`admin`、`web`（名字必须与 ci.yml 的 job 名逐字一致）
4. ✅ Require branches to be up to date before merging
5. ✅ Do not allow bypassing the above settings（防管理员侧门绕过）
6. ✅ Do not allow force pushes；✅ Do not allow deletions

备选（若安装 gh CLI）：
`gh api -X PUT repos/PuGaaa/HowDuoThink/branches/main/protection -f ...`
（以 UI 步骤为准，API 参数随 GitHub 版本变化。）
