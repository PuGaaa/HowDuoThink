# MySQL 8 备份与恢复

本文说明 `server/docker-compose.yml` 中的备份侧车、备份文件格式和安全恢复演练。当前脚本支持单库备份以及恢复到一次性验证库；它不覆盖线上业务库。

## 1. 备份设计与现状

`backup` 服务使用 `mysql:8.0` 镜像中的 `mysqldump`，通过 `MYSQL_DATABASE` 指定一个业务库，使用 `--single-transaction` 导出 InnoDB 一致性快照。启动后立即执行一次，此后每隔 `BACKUP_INTERVAL_SECONDS=86400` 秒执行；成功产物保留 7 天。最近执行状态记录在备份卷的 `last-status` 和 `last-success` 文件中，容器 healthcheck 检查状态和时间。

每次备份生成一个目录，内含：

| 文件 | 内容 |
|---|---|
| `database.sql.gz` | 单库 SQL 压缩文件 |
| `manifest.tsv` | 每张表的行数与数据哈希，以及 schema 哈希 |
| `info.tsv` | 创建时间、源库名、MySQL 版本、字符集和排序规则 |
| `SHA256SUMS` | 上述文件的 SHA-256 校验值 |

备份前会检查数据库仅含 InnoDB 基础表、每张表有主键，且没有触发器、存储过程或事件；dump 中不允许 `USE` 和 `CREATE DATABASE`。数据清单从同一份 dump 生成，不额外读取运行中数据库的行数。备份先在备份卷内写临时目录，校验完成后再原子改名为正式目录。

当前备份只写入 Docker 命名卷 `backups`。**没有已配置或验收的 OSS/异地复制、备份加密和外部告警；24 小时间隔尚无真实线上连续调度记录。** 不能把本地 Docker 卷当成主机损坏后的异地副本。

SQL dump 可能包含用户资料、投稿和学习数据。卷访问权限必须按生产数据管理；不要把 dump、备份卷或其副本上传到 CI artifact、公开存储或工单。应用卷本身未做静态加密。

## 2. 日常检查与手动备份

以下命令在 `server/` 目录执行：

```bash
docker compose ps backup
docker compose exec backup /ops/backup/health.sh
docker compose exec backup find /backups -mindepth 1 -maxdepth 1 -type d -name 'hdx-*' -printf '%f\n'
```

手动触发一次备份：

```bash
docker compose exec backup /ops/backup/backup.sh
```

脚本会输出产物目录，例如 `/backups/hdx-20261104T010203Z-abc123`。查看运行日志：

```bash
docker compose logs --tail=100 backup
```

查询卷对应的 Docker 卷名和挂载位置：

```bash
docker volume inspect server_backups
```

`server_backups` 是默认 Compose 项目名下的卷；自定义了 `-p` 或项目名时，替换为 `<项目名>_backups`。

不要在命令行参数中传数据库密码。侧车从 Compose 注入的 `MYSQL_PWD` 读取密码，密码不放在 `mysql` 或 `mysqldump` 参数中。

## 3. 安全恢复演练

`drill.sh` 仅用于验证归档。它会先校验 SHA-256 与 gzip，再拒绝含有切库/建库语句的 dump；然后创建随机命名的 `hdt_restore_*` 数据库，导入并比对恢复后的 schema、逐表行数和行哈希。脚本成功或失败都会删除本次创建的数据库，并清除临时纯文本 SQL；它不会选择、清空或覆盖源业务库。

执行示例，将 `ARTIFACT_DIR` 换成第 2 节列出的实际目录路径：

```bash
ARTIFACT_DIR=/backups/hdx-20261104T010203Z-abc123
docker compose exec -e DRILL_DIR=/tmp/restore-drills backup \
  /ops/backup/drill.sh "$ARTIFACT_DIR"
```

演练报告只保留数据库级汇总、逐表哈希清单和结果状态，不含 SQL 行数据；容器重建会清除 `/tmp/restore-drills`。

故障注入检查（损坏校验和、SQL 语句、数据哈希、数据库选择语句，以及备份/调度失败传播）：

```bash
ARTIFACT_DIR=/backups/hdx-20261104T010203Z-abc123
docker compose exec -e DRILL_DIR=/tmp/restore-drills backup \
  /ops/backup/verify-failures.sh "$ARTIFACT_DIR"
```

CI 同样运行 MySQL 8 服务、迁移当前 head、写入专用合成数据、备份并恢复到随机库。工作流只挑选 `result.tsv` 和 `business.tsv` 上传，并在上传前检查报告目录白名单与残留 dump；`.sql`、`.sql.gz`、校验清单和备份目录均不进入 CI artifact。

## 4. 线上故障恢复边界

当前已实现并演练的是**隔离库验证**，不是生产库覆盖恢复工具。发生线上数据故障时，先停止业务写入并保全故障库和日志；确认备份文件及校验和后，使用隔离库做恢复演练，核对迁移版本与关键业务数据，再制定新的恢复/切换步骤。不要把 `drill.sh` 用作线上恢复命令：它会在结束时删除自己创建的临时库。

数据库结构变更由 `server/alembic/versions/` 管理。执行版本回退前应完成备份并成功做隔离恢复演练；`0001_baseline` 回退会删除业务表。对没有 `alembic_version` 的旧库，先备份并检查实际 schema 与迁移链，不要直接执行 `stamp` 以掩盖结构差异。
