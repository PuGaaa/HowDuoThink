## 3 用户体验与学习路径

### 3.1 核心旅程

公开页面或分享进入 → 免费首关 → 完整复盘 → 第二关 → 第三关 → 登录保存 → 原目标关卡 → 次日再次训练。

| 场景 | 目标行为 |
|---|---|
| 游客进入免费题 | 允许进入，失败、重玩和复盘均不扣资格 |
| 第三关复盘 | 展示成绩与检查单，再给登录保存入口，不截断复盘 |
| 游客进入非免费题 | 说明保存和继续学习收益，携带目标 caseId 与来源进入登录 |
| 用户取消登录 | 留在原地图或复盘，保留成绩；不自动循环弹窗 |
| 登录成功 | 使用服务端真实用户 ID，归入试玩成果，收到保存确认后继续 |
| 登录成功但保存未完成 | 分开展示身份与保存状态，不提示云端已保存 |
| 目标题登录后仍受章节限制 | 定位该章，说明条件并展示跳级挑战入口 |
| 点击今日入口 | 只推荐当前可玩的题；游客仍在固定试玩池内 |

登录文案围绕“保存破案记录、诊断手册、跨设备继续”表达。保留章节顺序时不得使用“登录立即解锁全部章节”的承诺。

### 3.2 稳定主线与增量练习

- 固定试玩三个 ID，不能用包含社区题的动态排序前 N 项代替。
- 以迁移时核定的官方目录建立初始主线集合；官方来源不自动等于必修。
- 社区题与普通新增官方题默认归所属章选做区，不扩大旧主线的通关条件。
- 更新目录之前先冻结旧官方目录。客户端在覆盖 casepack 缓存、迁移本地 key 和采用新目录之前，按旧官方目录、该设备原有 casepack 缓存和本地进度计算解锁；云端按可证明的旧基线计算。确认档案归属后保存两者并集为 `unlockedChapterIds`，后续只增加。
- 已登录用户每篇首章可进入；其他章依主线前置完成或本章挑战成功解锁。挑战关由明确的主线配置确定，不能因社区题排序改变。
- 来源、主线属性和排序分别管理；章内区分主线、更多练习、社区实战。
- 未来更换课程主线需作为单独课程变更处理，保留用户既有资格。本轮不建设通用课程版本平台。

旧目录冻结产物至少包含案例 ID、章节、排序、挑战关与当时的解锁规则，并保存内容哈希用于核对。只能保留迁移时可证明的资格，不能恢复此前已丢失的解锁历史。

### 3.3 今日题与成长建议

建议游客优先继续未完成的试玩题，三关结束后提供重练或登录继续；已登录用户从当前可玩池推荐题。该规则会调整“同日全员同题”的旧约定，列为 D01 待确认。

成长目标先采用首关、三关、章节完成、跨层练习和错案重练等有业务含义的里程碑。称号具体门槛在首轮使用数据后确定，不以任意数字直接替换旧门槛。

## 4 账号与进度数据契约

### 4.1 身份和本地归属

手机与密码入口返回同一格式的真实 `userId`、资料与会话。账密按已有账号字段查询，不依赖 ID 前缀推导；用户名碰撞和大小写行为在变更查询前盘点，不能静默合并身份。

已登录密码账号通过验证码绑定手机号；后续手机登录继续使用原账号。手机号已属于另一账号时保留冲突结果，不按姓名或昵称自动合并两个账号。

本地空间分为 `guest:<guestId>` 和 `user:<userId>`。关卡进度、最后一局、检查单相关行为、任务、连续日期、待上传操作与同步时间均随空间归属。

新游客点击登录保存即确认当前游客成果归入该账号；成功后标记归属，不能再次导入其他账号。历史无归属 key 原样迁为独立历史档案，选择归属后一次性导入。旧账号的待传队列不得因切换身份转给新账号。

### 4.2 三类版本号

| 字段 | 含义 | 不得混用的对象 |
|---|---|---|
| `progress.revision` | 单用户进度投影的提交号 | 不是题目版本，也不是发布时间 |
| `contentRevision` | 单题内容、答案、动作与成本依据的修订号 | 不是全局 casepack 版本 |
| `cursor` | 案例发布提交的全局顺序，沿用现有分发版本概念 | 不是客户端内容新旧比较依据 |

评分算法另用固定 `scoringVersion` 标识。新结束局记录 `sessionId`、`caseId`、`contentRevision`、`scoringVersion`、当局专家成本、玩家成本、错误次数、结果与发生时间。

开局固定完整案例快照，最后一局复盘使用该快照。更新题目不得改变已开始的对局。不同内容版本的成本不直接比较为同一个最佳值；当前版本成绩和历史通过资格分开展示。

旧成绩版本未知，标为历史成绩，保留原值；不能赋成当前版本，也不能依据新成本重新评分。迁移可以为当前实际题目快照建立 revision 1，但不能倒推历史成绩都属于 revision 1。

### 4.3 同步协议

保留 `progress.payload` 作为读取投影，新增 `progress_ops` 作为已结算玩法操作的去重记录。客户端上传新操作，不再互相覆盖累计快照。

拟定 `POST /api/me/progress/sync`：请求为稳定 ID 的操作批次；响应为已确认操作 ID、完整进度投影和 `revision`。同一账号一次发一个同步请求。

服务端在同一事务内锁定该用户进度行、去重操作、应用新事实、更新投影并递增版本。结束局以 sessionId 唯一结算；检查单使用、立假设等未结束局行为采用独立操作 ID。重复请求返回已确认结果，不增加计数。

| 数据 | 结算规则 |
|---|---|
| 历史已通过资格 | 并集保留 |
| 当前版本最佳评级 | 明确按 S、A、B、F 排序，在同题同版本内比较 |
| 当前版本最低成功成本 | 只比较成功局，取最小值；无成功局为空，0 是有效值 |
| plays、fails、动物和行为次数 | 根据唯一操作累计，不能合并两份累计快照 |
| 每周三关 | 按该周成功的不同 caseId 计算 |
| 每周两个层 | 按该周成功案例的明确层标识去重；初期采用 chapterId |
| 每日复习、今日题 | 根据当天行为与案例身份结算，不重复完成 |
| 连续天数 | 由成功日期计算；日期统一北京时间，周一作为周起点 |
| 已解锁章节 | 只并集增加 |

旧云端 blob 作为一次性历史基线，旧累计与新操作分开结算，不补造旧事件和日期。只有 last/count 的旧连续记录保留历史显示；新的连续学习从实际可证明的日期计算。

`occurredAt` 为行为发生的 UTC 时间，服务端据此转换北京时间日周；`receivedAt` 只记录接收顺序。离线补传仍归行为发生周期。错案重练按失败与成功的发生先后判断；迟到操作需要重新计算受影响周期，不能依照上传先后判定“此前失败”。

客户端先持久化操作，再更新本地展示。请求开始时固定账号、token、操作批次和同步代次；应用响应后，在服务端结果上重放期间新增的未确认操作。退出与切号取消计时器，晚到响应不得更新当前其他账号。网络未完成的操作继续留在所属空间，下次同步仍使用原 ID。

### 4.4 旧协议与导入

旧 `POST /api/me/progress` 的全量覆盖写入在切换时停止，拟返回 HTTP 426；旧 GET 可保留读取。当前旧客户端只把非200显示为上传失败，服务端返回426不能让它自动出现升级提示。新客户端应识别该状态；已有H5通过部署更新，旧安装包通过明确的下载或更新入口升级。切换前告知旧版本将停止云同步，本地成果保留。禁止同时开放旧覆盖写和新操作结算。

新游客操作导入保持原 ID，服务端记录唯一归属。历史快照导入使用一次性导入标识，与新操作 ID 分开：历史通关和解锁取并集，未知版本的评级及成本作为历史记录保存。历史 plays、fails、动物等累计原值留在档案中，不与云端次数相加，也不计入当前日周任务或精确新操作数。云端已有基线继续保留，页面分开说明可证明的新记录与旧档案。一次性导入ID只能防重传，不能证明两份历史没有重叠；已经丢失的记录不在本次恢复承诺内。

## 5 内容生产与质量标准

### 5.1 选题和归类

每道题先记录训练目标、真实原型、与已有题的差异、前置能力、所属章节、关键证据和停止条件。按“学习目标、故障机制、证据形态、难度”查缺，不按章节题数排名扩产。

`chapterId` 决定 `part`，编辑选择章节后自动推导学习阶段；`domain` 和 `typeTags` 用于检索，不代替教学归属。章节目录、管理端选项、AI 候选和发布校验从同一份有效目录约束，不能各自接受未知章。

新增章节需要独立学习目标、足够的不重复候选题、首批核验完成题和维护者。具体数量门槛以审稿产能确定，本轮不创建新章。

### 5.2 四类质量验收

| 检查 | 必须成立 | 验收方式 |
|---|---|---|
| 技术事实 | 软件版本、异常消息、协议和修复机制有依据 | 原型证据、官方资料或最小复现 |
| 推理闭合 | 假设合理，动作可区分，时间线与影响分布一致，能合理停止 | 独立技术审阅 |
| 结构与评分 | 字段和引用有效、成本一致、标准路径可达、评分正确 | Node 与后端门禁及路径测试 |
| 可读可玩 | 遮住答案能推理，另一条合理顺序能走通，复盘无反向结论 | 非作者试玩 |

AI 可整理素材、提示缺证、辅助起草和检查文字矛盾，不能作为技术事实来源。缺少关键证据时先补件，不生成日志替投稿结论作证。教学重建保留机制关系并明确标识，不能冒充原始事故证据。

六维记录推理距离、证据形态、知识层次、反直觉度、跨层跨度、陷阱主动性，并引用题中证据。中位数半档与 L3 条件需先统一 D02；不能用两维 L3 自动覆盖中位数规则。学徒 L3 继续遵守工程约束的章尾限制。

### 5.3 存量校准

先冻结旧目录并精修三道免费题及首个登录后承接题 `async-swallow`，再分批覆盖 84 道成本差异与其余案例；承接题仍需登录，不扩大游客范围：

1. `first-npe` 修正 user/account 假设效应，核实“老用户偶发”的机制解释，重定成本；验收复盘假设板。
2. `caused-by` 核实异常包装与资源机制，避免把最底层异常等同业务根因的绝对表述。
3. `log-correlation` 补齐请求到具体实例的关联证据，解释实际超时来源，避免时间相关替代因果。
4. 对每个成本差异先判断必要证据、停止点和可选解释。纯解释移入复盘；必要动作保留并核定成本；同动作不能重复计费。
5. 人工确认标准链后再加入强制成本检查；不批量把 expertCost 改成任意动作相加。
6. T04A建立按ID、教学正文哈希和未校准项冻结的存量基线；未改动旧快照只读保留，不能冒充已校准题。新增题与任何发生教学内容修订的题执行严格门禁；初始化修订号、来源等元数据另留迁移审计，不能借元数据迁移修改正文。T04B逐项校准并移除对应基线，不能使用通配豁免或降低已校准题标准。
7. 免费三题和首个登录后承接题通过是首批内测条件；全量校准完成是扩量条件。A批可读未校准存量，但不无差别重发全库，不以存量历史导入触发新题发布流程。

每题保留原型或出处、六维依据、停止条件、标准路径、另一条合理路径、走验结果和修订原因。官方记录随文件与 Git 审阅保存；社区记录放受限编辑数据。

## 6 内容来源发布与修订

### 6.1 存储归属

| 阶段 | 官方内容 | 社区内容 |
|---|---|---|
| 选题 | `docs/出题总纲.md` | `submissions` 原稿及编辑归类 |
| 草稿与正文 | 工作分支 `app/data/cases/<id>.ts` | `cases.payload`，status=draft |
| 登记 | 审核后加入 `app/data/cases/index.ts` | 数据库记录，不加入 ALL_CASES |
| 发布输入 | 自动导出的 `server/seed/*.json` | 编辑确认的草稿 |
| 发布内容 | `cases` 官方发布副本 | `cases` 社区正式记录 |
| Web | `articles` 自动投影 | 同一投影机制 |
| App | 内置发布快照与 casepack | casepack 下载内容 |

官方 TS 是唯一创作源，后台官方正文与元数据只读。社区数据库是唯一创作源，不复制成官方 TS；精选仅增加展示入口和标识。导出 JSON、数据库官方发布副本和 App 缓存不成为另一处编辑入口。预留的 `content/seeds/`、`content/prompts/` 不在本轮启用，实际 Prompt 继续按业务归属维护。

### 6.2 统一发布事务

官方导入与社区发布复用同一 `cases` 公开服务：发布门禁、单题修订、全局 cursor、案例当前记录、文章投影和索引任务同事务提交。官方来源记录 Git 提交，社区记录编辑与投稿来源；内容相同不重复发布。

所有发布输入携带编辑时的 `baseRevision`，事务内与当前修订比较；一致才提交新修订，否则返回冲突并重新载入。官方TS显式携带目标 `contentRevision`，必须大于基准；社区由服务端在相同基准上生成下一修订。完全相同的已发布内容只跳过，不取新游标。Git提交只供追溯，不用于比较版本先后。

`contentRevision` 单调增加。退回旧内容时以当前修订为基准，以更高修订重新发布。旧seed、同修订不同内容、较低修订不同内容和陈旧编辑输入均不得覆盖新版。两位编辑从同一基准先后发布时，后一次返回冲突，不能因全局取号串行就覆盖前一人的正文。

T09A先盘点并归档包内官方正文和数据库已发布副本。相同快照可建立统一初始修订；有差异的同ID内容先核定，再发布更高修订。禁止让同一 `contentRevision` 对应两份不同内容。T09A交付能被App实际读取的修订和首批官方发布入口，之后T03才能记录新成绩；T09B补齐完整编审和维护功能。

发布后的社区题直接走重新发布，不先调用仅供 draft 的保存接口。编审中的修改不得立即覆盖线上正文。最小方案为编辑确认后原子重发布；若需跨会话保存新修订草稿，在 T09 细化时明确存储，不允许把线上题降为 draft。

### 6.3 分发和索引

- 同步先读取上界 head，再取 `since < cursor <= head` 的发布内容；并发发布取号串行化，不让较小号晚提交而被跳过。
- 客户端先持久化本批内容再保存 cursor；失败不能推进游标。
- 包内与远端同 ID 比较 `contentRevision`，取较新内容。章节、手册、每日题、题目查找使用同一有效案例集合并按 ID 去重。
- 索引任务携带 caseId、contentRevision 和发布快照，异步于 HTTP 请求执行。旧任务晚完成不能覆盖新索引，重复处理同一修订不重复落库。
- worker只消费任务中的发布快照，提交索引时原子比较已索引修订；较旧任务标记为已被替代。任务与已发布内容同事务创建，索引失败保留明确状态和重新处理入口；不用一次 HTTP 调用保证跨边界一致性。
- 本期不新增下架业务流程。若核实事实错误需要暂停分发，必须同时定义 App 缓存、casepack、Web 和 AI 索引的撤回语义，再实施该能力，不能只改数据库状态。

## 7 社区投稿与重复内容

### 7.1 从原稿到关卡

投稿 → 初审查重 → 补证与技术核实 → 脱敏确认 → AI 或人工起草 → 编辑补全 → 草稿试玩 → 发布 → 回告作者。

| 阶段 | 存储与权限 | 处理要求 |
|---|---|---|
| 原稿、补件 | submissions 及其受限补充记录，作者与编辑可见 | 保留原文和版本、时间、影响面、修复验证 |
| 脱敏素材 | 受限编辑记录 | 作者确认公开范围；AI 只读编辑确认的脱敏版本 |
| 编审记录 | 编辑专用记录 | 不塞入作者可见 review_note，也不放入公开 casepack |
| 关卡草稿 | cases draft | 明确章节、难度、假设、动作、评分与出处 |
| 玩法预览 | 已授权编辑预览 | 复用正式玩法，演练数据独立，不写真实进度、任务或运营统计 |
| 正式发布 | cases published 及派生产物 | 署名和来源关联完整，进入所属章选做区 |
| 作者结果 | 我的投稿 | 已采纳表示制作中；已发布才展示可玩和文章链接 |

材料不足继续待补充；不适合出题可以归档。当前没有独立的“投稿审核通过先发文章”通道，本轮也不扩建该通道。作者可反馈事实错误，编辑负责最终技术判断。

### 7.2 去重准则

| 情况 | 处理 |
|---|---|
| 同一用户同一次请求重传 | 返回原投稿，不重复建单 |
| 同一作者完全相同材料再次提交 | 关联原稿并提示已有记录 |
| 多位作者描述同一事故 | 核实后合并证据和有效贡献，制作一道题 |
| 同机制、同证据、同推理，仅换业务名称 | 补充既有题或归档，不新增关卡 |
| 同根因但有新的推理判断 | 明确相对已有题的新增价值后可新建 |
| 同症状不同根因 | 保留，可构成对照训练 |
| 相似材料但事实冲突 | 先核实，不直接合并 |

三次检查分别是提交时完全重复检查、人工或AI转稿前相似候选、发布前复查。两种转稿入口共用候选与编辑裁定。提交请求使用稳定请求 ID 与数据库唯一约束处理并发；格式归一只处理不改变语义的形式差异，保留原文、版本号、状态码和代码语义。

作者侧只推荐已公开内容；编辑侧同时查待审、草稿和已发布内容，不泄露他人私密投稿。检索复用现有 BGE 能力，按机制、证据和训练目标组织摘要；根因未核实时明确标记待核实。向量相似度只找候选，不能用未经标注验证的固定分数自动拒稿，也不能直接复用聊天检索的 0.15 门槛。

编辑写清相对哪道题新增了哪一步判断。补证合并不复制新题；实质变化才提高题目修订。多份投稿通过关联案例 ID 保留贡献，待审阶段可关联母投稿 ID；主要来源和有效补证署名分别展示。

两位编辑同时制作相似题时，候选应显示制作状态并集中处理；最终发布前以同组编审记录复核。语义是否重复仍由人决定，不声称检索能保证零重复。

## 8 学习指标与任务口径

### 8.1 最小事件记录

新增轻量产品事件表，记录 `eventId`、游客档案、服务端确认的用户、sessionId、caseId、contentRevision、事件类型、来源、发生时间和接收时间。账户身份由登录态确定；不记录手机号、token 或原始故障私密材料。

事件覆盖试玩进入、开局、结束、复盘、登录提示曝光、登录成功、成果导入和分享来源。每次真正重玩建立新 sessionId；页面 onShow、刷新复盘和请求重传不能建立第二个对局结束事件。

玩法结算和产品分析分工：成功结束等已结算事实可由 progress_ops 生成唯一分析记录；页面曝光单独记录。不得由两个入口分别计一次同一结束局。分析事件不承担成绩结算，不影响练习结果保存。

游客档案导入时只关联本次档案到目标账号，不能把同设备所有历史账号事件合并为一个人。预览、自动化和内部测试账号排除。

### 8.2 报表定义

| 指标 | 定义 |
|---|---|
| 首局成功率 | 同一首访批次中，首局成功人数除以首局开局人数，未结束单独显示 |
| 七日试玩三关完成率 | 首次试玩第0至第6个北京时间自然日内完成固定三题的主体数除以开始试玩主体数，仅取完整观察期 |
| 登录保存转化率 | 首次保存提示第0至第6个北京时间自然日内成功归入账号的主体数除以看到保存提示的主体数，仅取完整观察期 |
| 登录后继续率 | 首次保存完成第0至第6个北京时间自然日内完成至少一局的账号数除以成功保存账号数，仅取完整观察期 |
| D1 与 D7 有效训练留存 | 首次正式开局为第0日，第1或第7个北京时间自然日至少完成一局；只取观察期完整人群 |
| D7 成功破案留存 | 同一 D7 人群中至少成功一次；与结束失败局的有效训练留存分开 |
| 周活跃破案用户 | 北京时间周一至周日至少成功一局的去重用户数 |
| 题库完成度 | 已通过题目占题库比例，独立展示，不再冒充开局漏斗 |

首次正式开局指有效案例加载后建立sessionId并展示案情；有效训练则至少执行一次验证并结束对局，两者不能混为同一分母。成功与失败、首次与重玩分开查看。

未关联账号时主体为guestId；归入账号后以userId为主体，将该账号关联档案的事件合并，首次开局与首次提示分别取各自最早时间，三题完成按不同caseId累计。关联关系更新后重算对应首访批次。D1/D7成功与失败使用同一成熟首访分母，不再用不同档案分别计算一个账号。样本量、起止日期和未成熟观察期始终可见，不把缺少观察时间的用户当作流失。

首轮收集真实基线，不把 PRD 中未经验证的 30% 留存目标作为工程验收标准。修订题目影响题库规模时，不改变已发生漏斗事件的分母。

### 8.3 任务和提醒

每日复习按当日事件；每周三关按不同 caseId；跨层按不同 chapterId；错案重练要求此前确有失败且本次成功。同一局重传不涨任务，昨日和上一周事件不进入当前周期。

提醒先如实表述为页面存活时的浏览器提醒；关闭、修改时刻和权限状态与实际一致，不承诺关闭网页后的召回。后台推送列为独立后续能力。

## 13 上线顺序与回滚

同步协议切换包含破坏性行为，先在隔离存量副本完整演练，再用于业务环境。

1. 发布前导出版本、目录和数据盘点，完成恢复演练；如已有验证过的新协议兼容镜像，登记其为回退最低版本。首次切换没有该版本时，采用暂停写入与前向修复预案，不承诺退回旧覆盖写后端。
2. 短暂停止旧进度写入，等待在途旧请求结束，取得最终一致备份。
3. 新增迁移，建立云端历史基线与可证明的旧目录解锁资格，不改变历史成绩。客户端另在覆盖旧缓存、迁key前计算本地资格，确认归属后并集导入。
4. 启动新后端，验证旧POST拒写且数据不变；验证新sync、内容版本和健康状态。
5. 发布匹配的新客户端与Web，新版识别升级状态；旧H5部署更新，旧安装包通过明确入口升级。未更新旧版本会停止同步并可能仅显示上传失败，不能声称426会改变其原有界面；本地数据保留。
6. 按批次验收双账号、双设备和真实短信；A批验证真实H5直链，B批增加实际扫码。通过后开放当前批次内测。
7. 观察同步未确认操作、错误率、索引积压与用户反馈，再扩大使用。

回滚最低版本必须支持新操作协议和旧覆盖协议拒写。不能回退到继续全量覆盖进度的原始后端；不能为恢复可用而重新开放旧写入口。

新同步出现问题时暂停相应写入，保留本地队列和服务端操作记录，修复后按原ID重放。应用回滚不执行删除账本的数据库downgrade。恢复旧备份会丢失备份后新事实，必须按独立数据恢复事件处理，不能当普通镜像回滚。

内容回退发布新的更高修订。索引按源修订处理，不能把旧索引静默当新版已就绪。各环境使用同一实现，差异仅为连接、凭据、容量和域名。
