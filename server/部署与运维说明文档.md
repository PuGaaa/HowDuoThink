# server 部署与运维说明

## 三个文件各管什么

| 文件 | 职责 |
|---|---|
| `Dockerfile` | 造 api 镜像：Python 3.12 + pip 依赖 + 代码 + 启动命令（uvicorn，容器内 8001） |
| `docker-compose.yml` | 编排：起 mysql 和 api 两个容器、私有网络、卷、启动顺序 |
| `.env` | 该部署实例的全部配置（密钥/数据库/端口），**只在服务器上存在，永不进 git** |

## 环境模型：一个部署目录 = 一个环境 = 一份 .env

`.env` 不按环境类型起文件名，而是**每个部署实例一份**：键名统一（见 `.env.example`，
唯一允许进 git 的 env 文件），值各填各的；环境类型用文件里的 `ENV=dev|staging|prod` 表达。
三套环境同一套键名、同一个镜像，只有值不同——环境之间只允许配置不同（AGENTS.md 铁律）。

| | dev（本地） | staging（测试/预发） | prod（生产） |
|---|---|---|---|
| 文件在哪 | `server/.env.dev.local`（dev.sh 自动 source） | 测试机部署目录的 `.env` | 生产机部署目录的 `.env` |
| `ENV=` | `dev` | `staging` | `prod` |
| `MYSQL_DATABASE` | hdt | **hdt_staging**（库物理分开） | hdt |
| `JWT_SECRET` | dev 专用值 | 独立随机值 | 独立随机值，绝不与测试复用 |
| `DEEPSEEK_API_KEY` | 开发 key | 独立小额 key（好限额、好作废） | 生产 key |
| `WEB_ORIGIN` | localhost:3000 | 预发域名 | 正式域名 |
| `API_PORT` | （不走 compose） | 8002 | 8001 |

安全要点：

- **staging 也绝不填 `ENV=dev`**——dev 会打开 `/api/dev/login` 提权后门。
- 测试与生产最要紧的隔离是**数据库和 JWT_SECRET**，其余值填错都不至于出事故。
- 新环境上手：`cp .env.example .env` 然后填值。

## 同一台服务器跑测试 + 生产

一个部署目录 = 一个环境，目录名即 compose 项目名前缀，容器/网络/卷天然隔离：

```
/srv/hdt-staging/     # .env: ENV=staging, MYSQL_DATABASE=hdt_staging, API_PORT=8002
├── (git 检出)
└── .env
/srv/hdt-prod/        # .env: ENV=prod, MYSQL_DATABASE=hdt, API_PORT=8001
├── (git 检出)
└── .env
```

两套各自 `docker compose up -d --build`，得到 `hdt-staging-api-1` / `hdt-prod-api-1`
两组互不可见的容器；宿主机端口靠 `.env` 里的 `API_PORT` 错开。不需要改任何 yml。

## 首次上线（单机）

```bash
# 1. 装 Docker（宿主机唯一要装的东西）
curl -fsSL https://get.docker.com | sh
# 2. 拉代码 + 建配置（用 deploy key 拉私有仓库；不要 scp 拷目录）
git clone <repo> /srv/hdt-prod && cd /srv/hdt-prod/server
cp .env.example .env && vi .env          # 填真实值
# 3. 起整套（建表全自动：api 启动时 create_app 自动执行 alembic upgrade head
#    建表到最新版本，无需任何手工迁移步骤；自带初始管理员 admin / HaoDuo@2026——
#    首次登录后立即在管理端侧栏修改密码；ADMIN_PASSWORD 可覆盖默认密码）
#    ⚠️ 首次启动前 .env 必须已填 MYSQL_ROOT_PASSWORD——mysql 容器首次初始化依赖它，
#    缺失则 mysql 起不来；此时 api 会 fail-fast 报"MySQL 连不通"，根因不在 api，
#    排查要看 mysql 容器日志：docker compose logs mysql
docker compose up -d --build
# 4. 验证
docker compose ps                        # mysql healthy / api running
curl http://127.0.0.1:8001/api/health    # {"ok":true,...}
# 4.5 灌官方关卡（幂等，可重复跑；seed JSON 已由镜像构建期从 app/data/cases 生成）
docker compose exec api python seed.py
# 5.（可选）预热向量化模型，避免首个请求触发 ~100MB 下载
docker compose exec api python -c "from fastembed import TextEmbedding; TextEmbedding(model_name='BAAI/bge-small-zh-v1.5')"
```

反代（nginx/caddy，终结 HTTPS 后转本机 `API_PORT`）暂未纳入 compose；接好前 8001 只绑
`127.0.0.1`，公网摸不到，服务是安全的但外部不可访问。`COOKIE_SECURE=1` 要求 HTTPS 已就绪。

## 数据库迁移

schema 变更的唯一真相源是 `server/alembic/versions/`。本地、测试、生产一律
`alembic upgrade head`——api 容器启动时自动执行（boot-migrate，即上文首次上线第 3 步），
日常更新代码后 `docker compose up -d --build` 即可，无需任何手工迁移步骤。

版本速查（容器内看两个版本号是否一致，一致 = schema 已对齐当前代码）：

```bash
docker compose exec api python -c "from core import migrate; print(migrate.current_version(), migrate.head_version())"
```

**存量库升级硬步骤**（旧库的表建在迁移体系之前、没有 `alembic_version` 表，直接 upgrade
会因"表已存在"而失败——以下 stamp 流程已演练实测）：拉新镜像后、重启 api 前，先用新镜像
起一个一次性容器把当前库标记为基线（只写 `alembic_version`，不触碰业务数据）：

```bash
docker compose run --rm api python -c "from core import migrate; migrate.stamp_head(); print(migrate.current_version())"
# 输出 0001_baseline 即成功
docker compose up -d api     # 再重启 api；其后的非基线新版本走正常增量 upgrade
```

> ⚠️ **downgrade 警示**：`downgrade` 会 DROP 业务表（基线迁移的 downgrade 清全部业务表，
> 不删 `alembic_version`）——**任何 downgrade 前必须先手动备份**，步骤见 `docs/备份与恢复.md`。

开发约定：新增 schema 变更 = 在 `server/alembic/versions/` 加新迁移文件（单 revision
双引擎分支，SQLite / MySQL 走同一 revision），禁止手改已提交的历史迁移。

## 日常运维速查

```
docker compose up -d --build   # 首次上线 / 每次更新
docker compose ps              # 两项都应显示 running / healthy
docker compose logs -f api     # 盯后端日志（带 [rid] 的那种）
docker compose restart api     # 只重启后端
docker compose down            # 停止并删容器——卷保留，数据安全
docker compose down -v         # ⚠️ 连卷一起删——数据库和模型缓存全没，永不手滑
docker compose logs backup     # 备份侧车：每日自动备份（UTC 日界，保留 7 天）；
                               # 失败信号 = 日志出现报错或 /backups 当日无新文件
docker compose exec backup ls -lh /backups    # 查看备份产物；
                               # 手动备份 / 恢复步骤见 docs/备份与恢复.md
```

## 管理端与监控（2026-10 起随 api 容器一体部署）

管理端是独立工程 `admin/`（Vite + Vue3），构建产物打进 api 镜像（Dockerfile 多阶段构建），
由 FastAPI 托管在 `/admin/`。**部署命令不变**，一条 `docker compose up -d --build` 拉起整套；
compose 的构建上下文是仓库根目录（不再是 server/ 目录）。

- 管理端访问：`https://<域名>/admin/`；登录用 admin 账号（`ADMIN_PASSWORD` 引导创建的 `pw-admin`）
- CORS：管理端如独立域名部署，配 `ADMIN_WEB_ORIGIN`；同域托管（默认）无需配置
- 容器 healthcheck 已配：api 每 30s 自探 `/api/health`，`docker compose ps` 可见 healthy

### 系统设置（运行时业务配置）

管理端「系统设置」页（admin 专属）可即时调整业务策略参数，**不发版、不重启**：
游客门禁（免费章/关数，经 `GET /api/app-config` 下发 App）、AI 对话限流与成本单价、
短信验证码 TTL/重发间隔、登录防爆破阈值。优先级链显式且单一：
**settings 表（管理端写入）> 环境变量（部署默认值）> 内置默认**；
配置缓存在写时失效（单进程前提，与 ops 快照同），外部直改数据库需重启才生效。

### 错误追踪：Sentry（免费档，可选）

1. 注册 sentry.io → 建项目（FastAPI / Vue 各一个）→ 拿两个 DSN
2. server/.env 追加：
   ```
   SENTRY_DSN=<server 项目 DSN>
   SENTRY_ENV=prod
   ```
3. admin 前端 DSN 是构建期变量，在构建前导出（或写进 admin/.env.local）：
   ```
   VITE_SENTRY_DSN=<前端项目 DSN>
   VITE_SENTRY_ENV=prod
   ```
4. 重新 `docker compose up -d --build`。不配 DSN = 功能关闭，其余一切正常（运行时降级，非双方案）。

### 可用性告警：UptimeRobot（免费档，可选，强烈建议）

监控 `https://<域名>/api/health`（HTTP），挂了发邮件/IM。作用是覆盖"服务器断网/宕机/证书过期"
这类本机监控发不出告警的故障。免费档 50 个监控位足够。

### 服务自建监控

api 进程每 5 分钟（`OPS_SNAPSHOT_INTERVAL`）把请求/错误/耗时/内存/磁盘快照写入 `ops_snapshots`
（保留 `OPS_RETENTION_DAYS=30` 天），管理端「服务健康」页可视化。前提是单 uvicorn worker
（当前部署形态）；将来加 worker 需要换标准时序方案（remote_write 到 Grafana Cloud，不要挤在 2G 本机）。
