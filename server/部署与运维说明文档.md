# server 部署与运维说明

## 三个文件各管什么

| 文件 | 职责 |
|---|---|
| `Dockerfile` | 造纯 API 镜像：Python 3.12 + pip 依赖 + server 源码（容器内 8001），不构建前端 |
| `docker-compose.yml` | 编排：起 MySQL 8、api 和 backup 容器，管理私有网络、卷与启动顺序 |
| `.env` | 该部署实例的全部配置（密钥/数据库/端口），**只在服务器上存在，永不进 git** |

## 环境模型：一个部署目录 = 一个环境 = 一份 .env

`.env` 不按环境类型起文件名，而是**每个部署实例一份**：键名统一（见 `.env.example`，
唯一允许进 git 的 env 文件），值各填各的；环境类型用文件里的 `ENV=dev|staging|prod` 表达。
三套环境同一套键名、同一个 API 镜像，只有值不同——环境之间只允许配置不同（AGENTS.md 铁律）。

| | dev（本地） | staging（测试/预发） | prod（生产） |
|---|---|---|---|
| 文件在哪 | `server/.env.dev.local`（dev.sh 自动 source） | 测试机部署目录的 `.env` | 生产机部署目录的 `.env` |
| `ENV=` | `dev` | `staging` | `prod` |
| `MYSQL_DATABASE` | hdt | **hdt_staging**（库物理分开） | hdt |
| `JWT_SECRET` | dev 专用值 | 独立随机值 | 独立随机值，绝不与测试复用 |
| `DEEPSEEK_API_KEY` | 开发 key | 独立小额 key（好限额、好作废） | 生产 key |
| `WEB_ORIGIN` | localhost:3000 | 预发域名 | 正式域名 |
| `API_PORT` | （不走 compose） | 8002 | 8001 |

安全要点：

- **staging 也绝不填 `ENV=dev`**——dev 会打开 `/api/dev/login` 提权后门。
- 测试与生产最要紧的隔离是**数据库和 JWT_SECRET**，其余值填错都不至于出事故。
- 新环境上手：`cp .env.example .env` 然后填值。

## 同一台服务器跑测试 + 生产

一个部署目录 = 一个环境，目录名即 compose 项目名前缀，容器/网络/卷天然隔离：

```
/srv/hdt-staging/     # .env: ENV=staging, MYSQL_DATABASE=hdt_staging, API_PORT=8002
├── (git 检出)
└── .env
/srv/hdt-prod/        # .env: ENV=prod, MYSQL_DATABASE=hdt, API_PORT=8001
├── (git 检出)
└── .env
```

两套各自 `docker compose pull && docker compose up -d`，得到 `hdt-staging-api-1` / `hdt-prod-api-1`
两组互不可见的容器；API 镜像在 CI 构建，宿主机只拉取镜像。宿主机端口靠 `.env` 里的 `API_PORT` 错开。

## 首次上线（单机）

```bash
# 1. 装 Docker（宿主机唯一要装的东西）
curl -fsSL https://get.docker.com | sh
# 2. 只稀疏检出 server/ 部署目录；API 镜像已由 CI 构建并发布
git clone --filter=blob:none --sparse git@github.com:PuGaaa/HowDuoThink.git /srv/hdt-prod
cd /srv/hdt-prod
git sparse-checkout set server
cd server
cp .env.example .env && vi .env          # 填真实值
# GHCR 镜像为私有包：用 GitHub classic PAT（read:packages）登录，不要把 token 写进 .env
read -rp "GitHub 用户名: " GHCR_USER
read -rsp "GitHub Packages read:packages token: " CR_PAT; echo
echo "$CR_PAT" | docker login ghcr.io -u "$GHCR_USER" --password-stdin
unset CR_PAT GHCR_USER
# 3. 起整套（建表全自动：api 启动时 create_app 自动执行 alembic upgrade head
#    建表到最新版本，无需任何手工迁移步骤；自带初始管理员 admin / HaoDuo@2026——
#    首次登录后立即在管理端侧栏修改密码；ADMIN_PASSWORD 可覆盖默认密码）
#    ⚠️ 首次启动前 .env 必须已填 MYSQL_ROOT_PASSWORD——mysql 容器首次初始化依赖它，
#    缺失则 mysql 容器 init 失败退出、api 因 depends_on(healthy) 根本不会启动（看不到
#    api 的报错）；排查方向：docker compose logs mysql。若 mysql 在跑但 api 报
#    "MySQL 连不通"（fail-fast），则是网络/认证问题，同样先看 mysql 容器日志。
docker compose pull
docker compose up -d
# 4. 验证
docker compose ps                        # mysql healthy / api running
curl http://127.0.0.1:8001/api/health    # {"ok":true,...}
# 4.5 灌官方关卡（幂等，可重复跑；seed JSON 在 CI 导出后已装入 API 镜像）
docker compose exec api python seed.py
# 5.（可选）预热向量化模型，避免首个请求触发 ~100MB 下载
docker compose exec api python -c "from fastembed import TextEmbedding; TextEmbedding(model_name='BAAI/bge-small-zh-v1.5')"
```

反代（nginx/caddy，终结 HTTPS 后转本机 `API_PORT`）暂未纳入 compose；接好前 8001 只绑
`127.0.0.1`，公网摸不到，服务是安全的但外部不可访问。`COOKIE_SECURE=1` 要求 HTTPS 已就绪。
推荐同域反代统一路由：`/` → web（3000）、`/api/` → `API_PORT`、`/admin/` → `ADMIN_PORT`，
完整示例见下文「Web 社区站部署」。

## 短信认证（个人账号使用 PNVS）

本项目使用阿里云号码认证服务（PNVS）的短信认证 API，不使用要求企业资质的短信服务 `DysmsAPI SendSms`。个人认证账号可开通 PNVS 短信认证，无需申请企业资质、签名或模板；发送时必须选用 PNVS 控制台提供的系统签名与配套系统模板，不能填企业短信服务中的签名/模板。

开通后，在部署 `.env` 配置以下变量；开发、预发、生产使用同一套 SDK 与 API，仅值不同：

```dotenv
ALIYUN_PNVS_ACCESS_KEY_ID=
ALIYUN_PNVS_ACCESS_KEY_SECRET=
ALIYUN_PNVS_SIGN_NAME=
ALIYUN_PNVS_TEMPLATE_CODE=
```

AccessKey 使用专用 RAM 子用户，并只授予 `dypns:SendSmsVerifyCode`、`dypns:CheckSmsVerifyCode`。发送接口由阿里云生成验证码，数据库仅保留短信挑战的 `out_id`，不保存验证码明文；登录/绑定时再调用 `CheckSmsVerifyCode` 完成校验。当前服务仅支持中国大陆手机号（国家码 86）。

PNVS 短信认证需在控制台单独开通并计费，与阿里云短信服务的套餐和额度分开。可先在 PNVS 控制台绑定受控测试号码，再通过站点发送验证码、完成登录与账号互通验收。正式公网验收仍需 API 地址、HTTPS 和前端来源配置就绪。

参考：[个人开发者短信认证指引](https://help.aliyun.com/zh/pnvs/use-cases/sms-verify-for-individual-developers)、[发送验证码 API](https://help.aliyun.com/zh/pnvs/developer-reference/api-dypnsapi-2017-05-25-sendsmsverifycode)、[核验验证码 API](https://help.aliyun.com/zh/pnvs/developer-reference/api-dypnsapi-2017-05-25-checksmsverifycode)、[服务开通与计费](https://help.aliyun.com/zh/pnvs/getting-started/sms-authentication-service-novice-guide)。

## 数据库迁移

schema 变更的唯一真相源是 `server/alembic/versions/`。dev、测试、预发和生产统一使用
MySQL 8；新库由 api 启动时执行 `alembic upgrade head`，已有迁移记录的库在更新代码后也由
boot-migrate 升级。新增 schema 变更应新增迁移文件，不能手改已提交的历史迁移。

检查数据库当前版本和代码中的 head：

```bash
docker compose exec api python -c "from core import migrate; print(migrate.current_version(), migrate.head_version())"
```

已有业务数据、但没有 `alembic_version` 的旧库不属于新库安装流程。升级前先备份并在隔离库
恢复验证，再核对旧库实际表、列和索引是否与基线迁移相符；不要直接 `stamp` 以掩盖 schema
差异。迁移链不会自动补齐所有历史版本的缺列。完成核对后再按该库的版本状态制定迁移步骤。

任何生产 schema 操作前都应先备份，并在隔离库确认备份可恢复。`0001_baseline` 回退会删除
业务表；其他迁移的 `downgrade()` 也应逐条审阅。备份文件包含业务数据，不能留在公开路径或
作为 CI artifact 上传。完整操作见 [备份与恢复](../docs/备份与恢复.md)。

## 日常运维速查

```
git -C /srv/hdt-prod pull --ff-only  # 只更新稀疏检出的 server/ 文件
docker compose pull                # 拉取 CI 发布的 API 镜像
docker compose up -d               # 首次上线 / 每次更新
docker compose ps              # mysql、api、backup 均应显示 running / healthy
docker compose logs -f api     # 盯后端日志（带 [rid] 的那种）
docker compose restart api     # 只重启后端
docker compose down            # 停止并删容器——卷保留，数据安全
docker compose down -v         # ⚠️ 连卷一起删——数据库、模型缓存和本地备份全没
docker compose ps backup       # 检查备份侧车状态与 healthcheck
docker compose exec backup /ops/backup/health.sh   # 检查最近一次执行状态与时间
docker compose logs --tail=100 backup              # 查看调度日志
docker compose exec backup /ops/backup/backup.sh   # 手动触发单库备份
docker compose exec backup find /backups -mindepth 1 -maxdepth 1 -type d -name 'hdx-*' -printf '%f\n'
                               # 备份列表；隔离恢复演练见 docs/备份与恢复.md
```

## Web 社区站部署

社区站（`web/`，Nuxt 3 SSR）使用独立镜像 `ghcr.io/pugaaa/howduothink-web`，与 API 镜像分开构建、
拉取和重启。SSR 需要 Node 常驻进程（不是静态托管），容器内监听 3000，默认绑定 `127.0.0.1:3000`
（`WEB_PORT` 可改）。部署文件在 `web/`，与 Admin 一样单独检出：

```bash
git clone --filter=blob:none --sparse git@github.com:PuGaaa/HowDuoThink.git /srv/hdt-web
cd /srv/hdt-web && git sparse-checkout set web && cd web
cp .env.example .env && vi .env   # 填 NUXT_PUBLIC_API_BASE（完整 origin，如 https://hdx.com）
# GHCR 私有包登录步骤同 API 首次上线
docker compose pull && docker compose up -d
```

**`NUXT_PUBLIC_API_BASE` 必须是浏览器可达的完整 origin**：页面请求由浏览器直连 API
（`credentials: 'include'` 的 HttpOnly 会话 cookie），首页 SSR 期间也用同一地址取数。
因此推荐与 API 同域、由宿主机反代统一路由——cookie 不跨域、无需 CORS：

```nginx
server {
    listen 443 ssl;
    server_name hdx.com;                                    # 与 server/.env 的 WEB_ORIGIN 一致
    location /       { proxy_pass http://127.0.0.1:3000; }  # Nuxt SSR（web/.env 的 WEB_PORT）
    location /api/   { proxy_pass http://127.0.0.1:8001; }  # FastAPI（server/.env 的 API_PORT）
    # location /admin/ { proxy_pass http://127.0.0.1:18080; }  # 管理端独立域名部署时可去掉
}
```

同域部署下 `NUXT_PUBLIC_API_BASE` 填站点 origin；SSR 容器经公网域名回环取数，要求容器内能解析
并访问该域名。web 容器 healthcheck 每 30 秒自探首页，`docker compose ps` 可见 healthy。
暂不部署 Web 不影响 Server 与 Admin；反代未接时 3000 同样只绑 `127.0.0.1`，公网摸不到。

### 升级与存量重建（三段式文章）

社区文章三段式（问题 / 解决方案 / 根因与层契约）上线涉及三步，顺序不能颠倒：

1. **发布新 server 镜像**：API 部署目录内 `docker compose pull && docker compose up -d`。
   api 启动时自动执行 `0012_article_detail` 迁移给 articles 加 `detail` 列。迁移后、重建前，
   存量文章 detail 为空，API 自动降级输出（`problem=null`、`principles=[]`），旧 web 页面不受影响。
   schema 变更前建议先手动触发一次备份（`docker compose exec backup /ops/backup/backup.sh`）。
2. **重建存量文章投影**（幂等，可重跑）：

   ```bash
   docker compose exec api python ops/rebuild_articles.py
   ```

   预期输出 `重建完成：131/131 篇文章投影已升级为三段式`（分母为当前已发布案例数）。脚本复用
   发布事务里的同一派生函数，只写 articles 表、cases 零接触，并写回原 `published_at`，
   不打乱社区列表排序；单案例失败会带案例 id 终止，修复后重跑自动续上。dev 环境跑法见
   `server/ops/rebuild_articles.py` 文件头 docstring。
3. **发布新 web 镜像**：web 部署目录内 `docker compose pull && docker compose up -d`，
   详情页与列表页切换为三段式渲染。API 只加字段不改字段，web 未升级期间新旧页面均兼容。

## Admin 独立部署

Admin 使用独立镜像 `ghcr.io/pugaaa/howduothink-admin`，与 API 镜像分开构建、拉取和重启。
Admin 容器默认绑定 `127.0.0.1:18080`，由反向代理绑定到你选择的管理端域名；API 只提供 `/api/...`。
在后端 `.env` 中将 `ADMIN_WEB_ORIGIN` 填为完整管理端来源，供 CORS 校验。

Admin 的部署文件在 `admin/`，不是服务器 API 部署目录的一部分。部署 Admin 时单独检出 `admin/`，
运行 `docker compose pull && docker compose up -d`；如果暂时不部署 Admin，Server 不受影响。

API 容器 healthcheck 每 30 秒自探 `/api/health`，`docker compose ps` 可见 healthy。

### 系统设置（运行时业务配置）

管理端「系统设置」页（admin 专属）可即时调整业务策略参数，**不发版、不重启**：
游客门禁（免费章/关数，经 `GET /api/app-config` 下发 App）、AI 对话限流与成本单价、
短信验证码 TTL/重发间隔、登录防爆破阈值。优先级链显式且单一：
**settings 表（管理端写入）> 环境变量（部署默认值）> 内置默认**；
配置缓存在写时失效（单进程前提，与 ops 快照同），外部直改数据库需重启才生效。

### 错误追踪：Sentry（免费档，可选）

1. 注册 sentry.io → 建项目（FastAPI / Vue 各一个）→ 拿两个 DSN
2. server/.env 追加：
   ```
   SENTRY_DSN=<server 项目 DSN>
   SENTRY_ENV=prod
   ```
3. admin 前端 DSN 是构建期变量，在构建前导出（或写进 admin/.env.local）：
   ```
   VITE_SENTRY_DSN=<前端项目 DSN>
   VITE_SENTRY_ENV=prod
   ```
4. 在仓库 Secrets 配置 `ADMIN_SENTRY_DSN` 后，后续 main 发布会把它构建进 Admin 镜像；Server 镜像独立发布。不配 DSN = 功能关闭。

### 可用性告警：UptimeRobot（免费档，可选，强烈建议）

监控 `https://<域名>/api/health`（HTTP），挂了发邮件/IM。作用是覆盖"服务器断网/宕机/证书过期"
这类本机监控发不出告警的故障。免费档 50 个监控位足够。

### 服务自建监控

api 进程每 5 分钟（`OPS_SNAPSHOT_INTERVAL`）把请求/错误/耗时/内存/磁盘快照写入 `ops_snapshots`
（保留 `OPS_RETENTION_DAYS=30` 天），管理端「服务健康」页可视化。前提是单 uvicorn worker
（当前部署形态）；将来加 worker 需要换标准时序方案（remote_write 到 Grafana Cloud，不要挤在 2G 本机）。
